3字段引擎 — 探针机制

N1/N2/N3 共用同一套"设计探针 → 并行搜索 → 自适应深入 → LLM 合并"引擎。每个字段节点都是一次"广度 + 深度"的完整调研。

Step 1 — LLM 设计探针

design_probes(field_name, priors, stock_name, stock_code, ...)
  • 输入：前序报告（不截断） + 原始事件 + 公司认知 + 知识补充
  • LLM 输出 JSON：{"probes": [{"name":"...","task":"..."}], "coverage_note":"..."}
  • 探针数量由字段配置控制：N1/N2 为 3-6 个，N3 为 3 个
  • 每个探针的 task ≤300字，是完整的调研指令（非关键词）
  • 注入 CURRENT_DATE 确保时间感知

Step 2 — ThreadPool 并行执行

parallel_execute_probes(probes, engine="volc", max_workers=5)
  • 每个探针 = 1 次火山 Agent API 调用（结构化知识问答）
  • 火山 Bot ID: 7640524154441156122
  • 自动追加来源标注要求："每个关键数据标注来源（域名+日期）"
  • 失败自动重试 3 次（间隔 2s），不降级
  • 典型耗时：60-90s/探针，5 并行 ≈ 总耗时 ≈ 单个探针

Step 3 — 自适应深入探针

design_deep_probes(field_name, probe_results) → 0-2 个深入探针
  • LLM 阅读全部探针结论，判断：有料→深入 / 空的→换方向
  • 深入探针必须引用原探针的具体发现，不重复搜索
  • 最多 2 个深入探针，执行方式同 Step 2
  • 这是 V3 架构的核心创新：广度覆盖 + 深度挖掘的自适应平衡

Step 4 — LLM 合并报告

merge_probes(field_name, all_results) → Markdown 字段报告
  • 输入：第1轮探针（广度） + 第2轮深入探针（深度）
  • LLM 按字段专属 Prompt 合并为结构化 Markdown 报告
  • 数据质量规则：事实冲突必须裁决、禁止自行推算、口径统一
  • 输出：完整报告（不截断），写入 prior_reports 供下游使用

⚖️

事实冲突必须裁决

多源数据矛盾时，按 时效性 > 可靠性 > 具体性 优先级裁决。选择更可信版本作为基准，明确写出裁决理由和被否决版本。

"产能数据矛盾：A 源称 8万片/月（2024年报），B 源称 2.4万片/月（2025Q1）→ 裁决采用 B 源，因其更新且来自季度经营数据，A 源为全年累计口径"
🏷️

[推算] / [数据缺失] 标注

LLM 不得将推断内容伪装为事实。无充分证据时必须标注 [推算] 或 [数据缺失]，确保下游估值引擎不混淆事实与推测。

"毛利率压缩至 18-20% [推算：基于行业平均毛利率下降趋势外推]"
📏

数据口径统一

同一指标在不同来源中可能存在口径差异（总产能 vs 单一产品线产能，月产能 vs 年产能）。合并时必须统一口径或明确标注口径差异。

"8万片/月（全公司所有产品线合计）vs 2.4万片/月（仅第三代半导体产线）→ 统一为全公司口径"
🚫

禁止自行推算

只陈述探针结论中明确存在的事实。数字必须有源（域名+日期 / 字段名），无法追溯来源的数字不得写入报告。

"禁止: '35%关键设备依赖美国进口' → 必须: '35%关键设备依赖美国进口 (来源: semiengineering.com, 2025-06)'"
🕐

实时时间注入

所有 LLM 调用和火山搜索都注入 CURRENT_DATE。火山和大模型不知道今天几号，必须显式告知，确保"最新数据"的真实含义。

每次调用自动拼接: [当前日期: 2026-07-27]
✂️

零截断原则

所有字段（前序报告、公司认知、知识补充、搜索结果）完整注入 LLM 上下文，不做任何截断。宁可消耗更多 token，也不丢失信息。

原始事件、N0.5 公司认知、knowledge、step_one → 全部原文传入

5N5 事件推演 — 3 层因果递进

N5 不使用探针模式，而是 3 轮递进的深度推演。每轮 = 1 次火山搜索 + 1 次 LLM 分析，逐步从机理到量化到终判。

第 1 轮 · 事件机理

传导链拆解 + 不确定性清单

  • 事件 → 环节1 → 环节2 → ... → 财务指标
  • 每步标注：搜到了什么 | 没搜到什么
  • 与 N1 核心叙事：强化 or 动摇
  • 与 N2 竞争判断：验证 or 挑战
  • 输出：不确定性清单 → 交给第 2 轮
第 2 轮 · 深度追问

量化数据 + 历史参照 + 多方博弈

  • 回答第 1 轮的不确定性清单
  • 具体数字：产能/价格/市占率/营收
  • 历史参照：类似事件的历史结果
  • 多方博弈：同行反应、上下游动作
  • 标注：哪些置信度高、哪些仍模糊
第 3 轮 · 终判

断裂点 + 历史证伪 + 综合报告

  • 最可能断裂的环节
  • 历史证伪案例
  • 早期预警信号
  • 与市场共识对照：一致/超出/矛盾
  • 瓶颈节点（Baseline 脆弱点格式）

🔑 瓶颈节点输出格式（对接 Baseline 脆弱点分析）

- 环节名称: [具体环节] - 假设内容: [什么前提成立故事才能继续] - 反面证据: [什么事实会动摇这个假设] - 降级条件: [观察到什么信号说明脆弱点正在被激活] - 反身性风险: [股价本身的涨跌会不会改变基本面] - 量化边界: [产能/时间/供应量的具体上限] - 突破路径: [有没有可见的突破路径]

管线 B 特有逻辑 — 产业链上下文注入

管线 B 处理产业链表格记录时，会通过 source_record_id 关联天机卷中的同一条记录， 拉取 knowledge 和 step_one 字段。 同时将产业链表格中的 chain_analysis_json 和 top_nodes_json 构建为 industry_context，追加到 company_profile 中， 使字段分析能同时看到"个股事件 + 产业全局"两个维度。

7审计日志与容错

每次处理都留下完整审计轨迹。失败时回滚锁定状态，确保记录不会被永久跳过。

📋

JSONL 审计日志

每条记录处理完成后写入 reports/audit_logs/audit_YYYYMMDD.jsonl，包含 record_id、股票信息、耗时、各字段报告长度、写入状态、时间戳。

🔒

锁定 → 处理 → 标记/解锁

处理前先锁定（is_analyzing=true）。成功 → 标记已处理（is_analyzed=true）。失败/异常 → 解锁（is_analyzing=false），下轮重新处理。

🔄

火山重试策略

火山搜索失败自动重试 3 次（间隔 2s），不降级为博查。3 次均失败返回错误标记，由 LLM 在合并阶段处理缺失。

🚫

非 A 股主板跳过

N0.3 检查股票代码前缀（60/00/68/30），非 A 股主板直接标记天机卷已处理（is_analyzed=true），不进入后续分析。
