# 工作流管线详解

> 从产业资讯到最终估值报告的完整数据流、每一步的输入/输出/数据变换/错误处理

---

## 一、两条管线的全景

```
┌─────────────────────────────────────────────────────────────┐
│                     产业资讯 (新闻/公告/研报)                 │
└──────────────────────────┬──────────────────────────────────┘
                           │
          ┌────────────────┼────────────────┐
          ▼                                 ▼
┌─────────────────────┐          ┌─────────────────────┐
│  管线 1: 万业谱预研  │          │  管线 2: 估值引擎    │
│  (Coze 工作流)      │          │  (Python 编排器)    │
│                     │          │                     │
│  事件→5维语料       │          │  股票代码+事件      │
│  存入Coze万业谱DB   │─────────▶│  →完整估值报告      │
│                     │  语料    │                     │
└─────────────────────┘  输入    └─────────────────────┘
```

**管线 1** 是"语料工厂"——从产业资讯中提炼结构化的投资研究语料。
**管线 2** 是"估值引擎"——基于语料和财务数据，生成完整的估值重构报告。

两条管线可独立运行，也可串联（管线 1 产出作为管线 2 的 Agent-0 输入）。

## 二、管线 1: 万业谱预研（详细步骤）

### Step 1: N0 — 股票代码验证

```
输入: 用户输入的股票代码/名称 (可能不规范)
处理:
  1. 新浪行情 API 精确代码查询 (sh{code}, sz{code})
  2. 新浪 suggest API 模糊名称搜索
  3. 返回验证结果
输出:
  {
    is_valid: bool,
    verified_name: str,
    stock_code: str,       # 6位纯数字
    stock_market: str       # "SH" / "SZ"
  }
错误: 无效代码 → 标记，不进入后续节点
```

### Step 2: N1 — 事件消化 + 探针设计

```
输入:
  - news_content: 原始资讯全文
  - knowledge: 背景知识
  - step_one: Agent-0 初步分析 (如有)
  - stock_name, stock_code

LLM 调用: deepseek-v4-flash, max_tokens=4096, temperature=0

处理:
  1. 消化事件核心要点 (what changed, why matters, who benefits)
  2. 设计 15 个研究探针 (5 字段 × 3 个)
  3. 探针设计原则: 具体、可执行、信息不重叠

输出:
  {
    event_type: str,
    event_summary: str,
    probes_map: {
      "industry_expert_research": ["探针1", "探针2", "探针3"],
      "adversarial_thinking": [...],
      "investment_theme": [...],
      "future": [...],
      "event_deduction": [...]
    }
  }

错误: JSON 解析失败 → Code 节点清洗 → 重试一次
```

### Step 3-7: N2-N6 — 5 字段并行探针执行

```
每个节点的内部流程 (field_node.py):

┌─ Step A: 读取前序报告 ───────────────────┐
│  按 PRIOR_FIELDS 顺序读取已完成字段的报告   │
│  N2(investment_theme): 无前序              │
│  N3(industry): 读取 N2                     │
│  N4(adversarial): 读取 N2+N3              │
│  N5(future): 读取 N2+N3+N4               │
│  N6(event_deduction): 读取 N2+N3+N4+N5   │
└───────────────────────────────────────────┘
                    ↓
┌─ Step B: LLM 设计探针 ────────────────────┐
│  基于前序认知 + 本字段视角                 │
│  LLM: deepseek-v4-flash, max_tokens=8192  │
│  探针数: PROBE_MIN ~ PROBE_MAX 个          │
│  输出: JSON {"probes": ["p1", "p2", ...]} │
└───────────────────────────────────────────┘
                    ↓
┌─ Step C: ThreadPool 并行执行探针 ─────────┐
│  每个探针独立上下文                         │
│  LLM: deepseek-v4-flash (Function Calling) │
│  工具: bocha_search (最多2次/探针)          │
│  最多 8 轮 FC 迭代                          │
│  输出: 每探针 4 项结论 (发现+数据+推断+缺口) │
└───────────────────────────────────────────┘
                    ↓
┌─ Step D: LLM 合并探针 → 字段报告 ─────────┐
│  LLM: deepseek-v4-flash                    │
│  按字段专属模板合并为结构化报告              │
│  输出: 字段报告 (Markdown)                  │
└───────────────────────────────────────────┘
```

5 个字段的输出报告格式:

| 字段 | 输出章节 |
|------|---------|
| investment_theme | 核心叙事 / 变革证据链 / 关注度评估 / 估值锚与信息差 / 关键验证节点 |
| industry_expert_research | 产业链位置 / 供给格局与价值捕获 / 卡点检查 / 天花板量化 |
| adversarial_thinking | 核心假设脆弱性 / 两大失效测试 / 利益博弈 / 外部冲击 / 论点破裂条件 |
| future | 催化日历表格 (预计时间/事件/证实条件/证伪条件/优先级) |
| event_deduction | T+30/T+90/T+180推演路径 / 论点破裂场景 / 历史案例参考 |

### Step 8: N7 — 总装 + 去重 + 交叉验证

```
输入: 5 份字段报告 + stock_code + stock_name + event_date + 其他元数据

LLM 调用: deepseek-v4-flash, max_tokens=8192, temperature=0

处理:
  1. 去重: 相同事实在多份报告中重复 → 保留在语义最匹配的字段
  2. 交叉验证:
     - ier vs theme: 产业链判断与投资叙事是否自洽？
     - adv vs ded: 风险判断与事件推演逻辑是否一致？
     - 不一致处标注"存在分歧"
  3. 补充: 5 份报告共同遗漏的信息 → knowledge_supplement

输出:
  {
    industry_expert_research: str,    # 去重后
    adversarial_thinking: str,        # 去重后
    investment_theme: str,            # 去重后
    future: str,                      # 去重后
    event_deduction: str,             # 去重后
    knowledge_supplement: str,
    cross_validation: {
      consistencies: [...],
      divergences: [...]
    }
  }

错误: JSON 解析失败 → 重试一次
```

### Step 9: N8 — 写入 Coze 数据库

```
输入: N7 的 final_record

处理:
  1. POST 万业谱 Coze DB
     - 14 个字段，每字段截断 10000-15000 字符
     - 含 stock_code, stock_name, event_date, event_source,
       raw_event_text, response_level, preliminary_reasoning,
       5 个分析字段, knowledge_supplement, uuid,
       source_record_id, is_complete, created_at

  2. PUT 天机卷 Coze DB
     - 标记 is_analyzed = true
     - 防止重复处理

错误:
  - Coze API 超时/失败 → 不阻塞，记录日志
  - 写入失败 → 后续调度器重试
```

## 三、管线 2: 估值引擎 V8（详细步骤）

### Step 0: 预筛选 (PreScreen Gate)

```
输入:
  - stock_code, stock_name
  - 投资主题 + 产业链报告 (来自万业谱或直接输入)
  - 事件描述
  - 市值 (来自 investoday)

LLM 调用: deepseek-v4-flash, max_tokens=4096

处理:
  1. 4 维评分 (同源性 1-10 + 暴露度 1-10 + 弹性 1-10 + 产业链地位 1-10)
  2. 裁量调整 ±3
  3. 规则判断

通过规则:
  - 同源性 ≥ 4 (不是平行线)
  - 总分满足市值阶梯门槛:
    市值≤300亿 → 总分≥20
    市值≤500亿 → 总分≥28
    市值>500亿 → 总分≥28

输出: PreScreenResult { passed: bool, scores: {...}, summary: str }

错误:
  - Flash 不可用 → 默认放行 (fail-open)
  - JSON 解析失败 → 默认放行
```

### Step 1: Agent-0 — 预路由

```
输入:
  - stock_code, stock_name
  - 万业谱预研语料 (可选)
  - 事件标签 (可选)

处理 (纯规则引擎，无 LLM):
  1. 行业分类识别 (申万 L1/L2/L3 → 专项数据包映射)
  2. 事件标签解析 (产能释放/壳重组/管线进展/政策催化/困境反转)
  3. 数据需求清单生成:
     - core_mandatory: 所有标的必需的端点
     - specialized_optional: 行业专项端点
     - optional_ignore: 不需要的端点
  4. 模型提示 (非绑定)

输出:
  {
    stock_code, stock_name, industry,
    data_requirements: {
      core_mandatory: [...],
      specialized_optional: [...],
      optional_ignore: [...]
    },
    model_hint: str,
    research_context: str
  }
```

### Step 2: Agent-1 — 数据锻造

```
输入: Agent-0 的 data_requirements

处理 (纯数据抓取 + 交叉验证，无 LLM):
  Phase 1: investoday 核心数据 (8 个端点，parallel)
    - 实时行情 / 估值指标 / 利润表TTM / 资产负债表TTM /
      现金流量表TTM / 财务衍生指标 / 盈利能力 / 行业分类

  Phase 2: investoday 专项数据 (6 个端点，parallel)
    - 杜邦分析 / 分部收入 / 一致预期 / 经营评述 /
      综合得分 / 事件窗口股价

  Phase 3: Tushare 补充数据 (10 个端点，parallel)
    - 日线 / 日线指标 / 资产负债表Q / 利润表Q / 现金流量表Q /
      财务指标 / 主营构成 / 业绩预告 / 业绩快报 / 股东户数

  Phase 4: 交叉验证 (8 项)
    - 毛利率 / 净利率 / ROE / ROIC / EPS /
      资产负债率 / 营收TTM / 经营现金流
    - 容差标注，不阻塞

  Phase 5: 数据质量评分 (0-100)

输出:
  {
    request_id, stock_code, stock_name, industry,
    packages: {
      core: { fields: {...}, quality: str },
      specialized: { fields: {...}, quality: str },
      optional: { fields: {...}, quality: str }
    },
    cross_validation: {...},
    overall_data_quality_score: float,
    fetch_errors: [...],
    event_date: str,
    event_window_prices: {...}
  }

错误:
  E101: core_package 关键字段缺失 → 硬终止
  E102: investoday 部分端点超时 → quality=partial
  E103: Tushare 不可达 → 跳过
  E104: 交叉验证超容差 → 标记不阻塞
```

### Step 2.5: Agent-Baseline — 投资地图

```
输入:
  - Agent-0 预研语料 (industry_expert_research, investment_theme, knowledge_supplement)
  - Agent-1 财务数据 (core fields, product mix, forward signals)
  - 火山搜索 (分部数据, 可比公司)

LLM 调用: deepseek-v4-pro, max_tokens=8192, temperature=0.1

处理:
  单次 LLM 调用 → 六维投资地图 (Markdown)

输出: 投资地图报告 (~2000-4000 tokens)
  一、公司身份与收入结构 (产品/分部表格)
  二、财务基线 (ROIC vs WACC, 盈利质量, 现金流)
  三、产业位置 (五力, 护城河三层拆解)
  四、增长轨迹 (历史趋势, 产能, 前瞻信号)
  五、投资主线与脆弱点 (关键假设+反面证据+降级条件)
  六、量化锚点 (产能/价格/市占率/壁垒/弹性 表格)

错误: LLM 不可用 → 跳过，下游 Agent 直接消费原始数据
```

### Step 3: Agent-2 — 统一路由判官

```
输入:
  1. 投资地图 (Agent-Baseline)
  2. 估值倍数全矩阵 (PE/PB/PS + 历史分位)
  3. 定量定价工具 (反向DCF/CAGR/ROE)
  4. 事件语料 (投资主题/事件推演/行业研究/火山搜索)
  5. 前瞻信号面板 (格式化文本)
  6. 代码约束清单 (每模型的技术可行性观测)

LLM 调用: deepseek-v4-pro, max_tokens=40960, temperature=0

处理:
  6 步强制推理链:
  Step 1: 理解公司 (消费投资地图)
  Step 2: 识别估值锚 (SOTP先判 → 叙事→锚 → 数字验证)
  Step 3: 事件光谱诊断 (3维打分 → 分布形状)
  Step 4: 模型选择 (锚匹配 → 叙事契合 → 数据兼容)
  Step 5: 计价判断 (not_priced/partially/fully/unknown)
  Step 6: 信号审核 (轻量级，匹配度 0-10)

输出:
  {
    market_narrative: {
      core_bet, narrative_lifecycle,
      primary_anchor, primary_anchor_evidence,
      anchor_conflict, narrative_summary,
      secondary_anchors, anchor_shift_potential
    },
    event_profile: {
      distribution_shape, shape_rationale,
      timing_certainty, outcome_binaryness, precedent_richness
    },
    routing_decision: {
      primary_model, model_category,
      routing_reason, validation_models,
      validation_rationale, validation_strategy,
      code_constraints_discussion,
      sotp_primary_segment_model, event_driven_segment
    },
    pricing_assessment: {
      overall_priced_in, priced_in_rationale,
      priced_in_estimate, residual_catalyst
    },
    signal_audit: {
      key_supporting_signals, key_conflicting_signals,
      match_score, score_rationale
    }
  }

错误:
  LLM 不可用 → _fallback() 纯代码路由 (硬约束字典)
  JSON 解析失败 → parse_json 4层容错 → 仍失败 → fallback
```

### Step 4: Agent-3 — 情景估值 + 非对称性

```
输入:
  - Agent-2 路由决策 (primary_model, anchor, event_profile)
  - Agent-1 数据包 (完整财务数据)
  - Agent-Baseline 投资地图
  - 事件语料 (event_deduction, adversarial_thinking, future)
  - 火山搜索数据
  - WACC 预计算结果 (代码计算)
  - BS 画像预计算结果 (代码计算)
  - 前瞻信号面板

═══════════════════════════════════════════
Phase 1: 代码预计算 (无 LLM)
═══════════════════════════════════════════

WACC 计算:
  - rf: 10年期国债收益率 (investoday API)
  - beta: vs CSI 300, 1年日线数据
  - ERP: 动态ERP (波动率调整)
  - 信用利差: 按负债率分档
  - WACC = rf + beta × ERP + credit_spread

BS 画像:
  - 盈利锚 → 反向 DCF (二分法求隐含 g)
  - 收入锚 → 隐含 CAGR (PS → 3年收入CAGR)
  - 资产锚 → 隐含 ROE 改善 (PB → ROE gap)

═══════════════════════════════════════════
Phase 2: LLM-1 情景推导
═══════════════════════════════════════════

LLM 调用: deepseek-v4-pro, max_tokens=40960, temp=0.1, thinking=max

处理:
  执行清单 (递进推理链):
  1. 素材吸收 (投资地图 + 2a结论 + 事件锚点)
  2. 引用 2a 诊断结论
  3. 三情景因果推演
     3a. 分布形状 → 参数上限
     3b. 事件冲击量级 → 参数幅度
     3c. 投资命题 + 因果分叉点
     3c-补充. CAGR 拆解 (量增/涨价/结构升级)
     3d. 因果剧本 (先写故事)
     3e. 赋参数 (PE/PS/PB/CAGR/ROIC/RR)

输出: LLM-1 参数输出 (JSON)
  - reasoning_trace: 完整推理链
  - growth_path_decomposition: CAGR 拆解表
  - scenario_details: 三情景参数
  - data_gaps: 数据缺口
  - change_request: 搜索请求

═══════════════════════════════════════════
Phase 3: 代码计算层 (无 LLM)
═══════════════════════════════════════════

对 LLM-1 的三情景参数，用精确公式计算估值:

  模型 A: MCAP = IC × (ROIC%/100) × PE
  模型 B: MCAP = Revenue × (1+CAGR)³ × PS
  模型 D: MCAP = Equity × PB
  模型 K: MCAP = Σ[FCFF_t/(1+WACC)^t] + NOPAT_N×PE/(1+WACC)^N
  ... (其他模型)

产出:
  - 每情景: target_mcap_yi, upside_pct
  - 概率加权: weighted_mcap, weighted_upside
  - ROIC 审计: ROIC vs WACC, g vs ROIC×RR 一致性
  - 跨族校验: 校验模型估值 (如有)

═══════════════════════════════════════════
Phase 4: LLM-2 审阅 + 搜索
═══════════════════════════════════════════

LLM 调用: deepseek-v4-pro, max_tokens=40960, temp=0.1, thinking=enabled
多轮对话: 最多 3 轮, 每轮最多 2 次并行搜索

处理:
  Task 0: 事件锚点校验 (价格/产能/时间线逐项对照)
  Task 0.5: 前瞻信号验证 (搜索最新数据 → 对照 LLM-1 解读)
  Task 1: 数据补充 (逐条搜索 data_gaps + change_request)
  Task 2: 逻辑审查 (从 reasoning_trace 找参数-推理矛盾)
  Task 3: 参数修改 (发现问题必须改 → change_log)
  Task 4: 最终判断 (置信度/交易标注/KPI/叙事)

输出: 完整最终报告 (JSON)
  - scenario_valuation (可能修改后的参数)
  - 代码重新计算后的估值结果
  - change_log (路径+旧值+新值+理由+证据)
  - confidence (4维)
  - trade_annotation (tier + 4维)
  - monitoring_kpis (4类)
  - narrative (150-300字)
  - expectation_gap
  - validation_crosscheck

错误:
  E301: LLM-1 JSON 解析失败 → 重试
  E302: LLM-1 超时 → 重试
  E303: LLM-2 API 错误 → 用 LLM-1 参数 + 代码修正模式 (跳过审阅)
  E304-E307: 一致性校验失败 → 在报告中标注，不阻塞
  E400: 代码计算异常 → 用 LLM 原文估值 fallback
  E401: 三情景概率和≠1.0 → 自动归一化
```

### Step 5: 报告生成

```
输入: Agent-3 最终输出

处理:
  1. Markdown 渲染 (valuation_app/main.py: export_markdown)
     10 个章节:
       一、估值路由 (模型选择+理由)
       二、市场检测 (定价程度+隐含预期)
       三、参数校准 (参数表+来源)
       四、预期差 (市场vs我们)
       五、三情景推演 (bear/base/bull 详情)
       六、案例比对 (V3 案例库匹配)
       七、置信度 (4维)
       八、交易标注 (tier+建议)
       九、追踪框架 (KPI+触发器)
       十、投资叙事

  2. JSON 序列化 (完整结构化数据)

  3. 保存到 reports/ 目录

  4. (可选) 写入 Coze 估值输出数据库
```

## 四、评测模式

```
orchestrator.run_pipeline(eval_mode=True)

与正常模式的区别:
  1. 跳过 Agent-0 (不从 Coze 拉取预研语料)
  2. 跳过 Agent-1 (不从 investoday/Tushare 拉取数据)
  3. 使用 frozen 数据 (预先准备的 test_data/)
  4. 产业链分析也禁止联网搜索 (防止未来信息泄露)

目的: 评测历史案例时，当前网络搜索结果已包含事后涨幅信息，
      会污染 LLM 推理。评测模式确保 LLM 只能基于历史时间点的信息。
```

## 五、错误码参考

| 错误码 | 来源 | 含义 | 处理 |
